# TRPG学習データ 品質評価基準（100点満点）

このファイルは `training/` の学習データ（raw レコードおよび `messages` 化後のサンプル）を
評価するための**定義書**である。実装ではなく、評価者が同じ基準で点を付けられることを目的とする。

## 0. 基本原则

1. **スキーマ合格と文章品質は別物。** スキーマ検証は「アプリが受理する形か」を判定するだけで、
   「良いGM応答か」「正しく抽出できているか」は判定しない。したがって機械点と人手点を分離する。
2. **274件は検証用サンプルであり正解ではない。** 機械検証を通ったことは最低条件であって
   高品質の証明ではない。採点結果は基準の較正に使い、正解ラベルとして扱わない。
3. **赤線項目は点数に関係なく人間確認。** 出目創作・敵HP操作・事実の捏造・GM秘密の漏洩などは
   部分点で相殺しない。
4. **70点以下は人間による確認対象。** 70点を超えても赤線項目があれば確認対象とする。
5. **Kotlinの受理仕様と学習データの推奨仕様を分ける。** Kotlin/Ktx が受理するかは
   「アプリが落ちないか」の問題であり、学習データとして望ましいかは別問題である。
   両者が矛盾するときは、どちらが「受理」でどちらが「推奨」かを明示し、
   受理側を書き換えて矛盾を解消してはならない（今回の評価ではコード・プロンプト・スキーマ自体は変更しない）。

### 根拠の階層

| 層 | 根拠 | 評価での役割 |
|---|---|---|
| 受理仕様 | `core/` の Kotlin データクラス・パーサ・バリデータ | 何がアプリに通るかを決める。スキーマ error の判定基準 |
| 生成指示 | `training/tools/prompts.py` の `SYSTEMS`、`AdventureCreator.kt` のプロンプト | 学習データに書くべき値・文体を決める。忠実性の判定基準 |
| 検証器 | `training/tools/schema_lib.py`, `build_dataset.py`, `verify_*.py` | 上記を機械的に写したもの。写しが古い場合は Kotlin 側を正とする |
| 人手判断 | この定義書の項目7〜10 | 意味・自然さ・TRPG整合性を判定する |

### 機械項目の減点方法

- **項目2（15点）**: `schema_lib.validate_output()` が1件でも error を返したら **0点**。
  warning は1件につき -2点（下限0）。
- **項目1（10点）**: JSONパース不可・トップキー過不足・`messages` の role 不正・
  `assistant.content` が compact JSON でない・コードフェンス混入のいずれかで **0点**。
  部分的な問題（改行位置など）は -3点。
- **項目3（10点）**: 未知ID参照1件 -3点、存在しないスキルID -3点、
  group の混在（別シナリオが同じ group） -5点。違反がなければ10点。
- **項目4（10点）**: 判定式・出目数・HP範囲・quantity上限・FLAG_KEY形式の
  違反1件につき -3点。敵HP変更は赤線（後述）により別途扱う。
- **項目5（5点）**: 完全一致重複1件 -5点、近似重複（Jaccard ≥ 0.85）1件 -3点、
  同一 group が全件同じ系統のバリエーションのみなら -2点。
- **項目6（5点）**: `check_simplified_chinese.py` の検出1件（出現1回）につき -1点、
  `check_protected_text.py compare` で保護フィールド変化1件 -5点。
  `check_protected_text.py scan` は「行単位」の補助情報であり、減点の集計単位には使わない（後述）。

※ 機械項目で0点になっても人手項目の採点は続け、合計点と赤線の両方を記録する。

### 人手項目の採点アンカー

| 項目 | 満点 | 部分点 | 0点 |
|---|---:|---:|---:|
| 7 指示忠実性 | 入力の要求をすべて満たす | 一部の指定が曖昧／省略 | 指示と無関係な出力、別タスクのスキーマ |
| 8 情報正確性 | 追加も欠落もなし | 推測が1〜2箇所あるが事実は不変 | 事実の捏造、否定反転、秘密開示 |
| 9 日本語品質 | 自然で読みやすい | 不自然な表現が1〜2箇所 | 意味が通じない、簡体字多発 |
| 10 TRPG整合 | 世界・判定・状態が矛盾ない | 細かな矛盾が1箇所 | 判定無視、敵HP操作、状態改変の直接記述 |

## 2. 共通の機械チェック（根拠ファイル）

評価基準は次の実装に照らして定義する。Kotlin実装側の変更時はこれらを同期する。

| 判定内容 | 根拠 |
|---|---|
| キー集合・型・列挙・文字数/件数上限 | `training/tools/schema_lib.py`（`validate_gm`, `validate_world`, `validate_character`, `validate_items/locations/npcs/quests`, `validate_extraction`） |
| 封筒キー・category/task整合・request/context存在 | `training/tools/build_dataset.py` の `record_problems()`, `iter_raw()` |
| `messages` 化・role順序・compact JSON | `build_dataset.py` の `to_messages()`, `verify_sft_outputs.py` |
| 完全一致・近似重複 | `build_dataset.py` の `exact_seen`, `near_duplicates()`（6-gram Jaccard ≥ 0.85） |
| group単位の分割・漏洩なし | `build_dataset.py` の `assign_splits()`, `verify_dataset.py` |
| 自然文フィールドの保護 | `check_protected_text.py` の `ALLOWED_FIELDS`, `scan`, `compare` |
| 簡体字検出（主） | `check_simplified_chinese.py`（`误` / `录` / `采` を含む。**出現回数**で集計、`采配`/`采女` はホワイトリスト除外） |
| 簡体字検出（補助） | `check_protected_text.py scan`（**行数**で集計。旧方式の参考情報として残す） |
| 推敲差分の意味リスク | `yomiyasu_compat.py` 経由の `yomiyasu_diff.py --fail-on=meaning-risk`（補助。合格判定はしない） |

`prompts.py` の `SYSTEMS` は評価時の「指示」そのものである。
- `gm`: サイコロを振らない／状態変更は `stateChanges` に宣言／GM専用情報の非開示／
  選択肢3〜4／判定が必要な選択肢だけ `check`／JSON1つだけ。
- `world_json`: 16キーすべて／日本語／固有名詞の焼き写し禁止／`secrets` はGM専用／
  配列は配列のまま／数値は数値／`combat.hp` 1〜30。
- `extraction_*`: 書かれていない事実を作らない／該当なしは空配列／数値・真偽値の型維持。

`render.py` は `PromptBuilder.kt` と同じ組み立てである。評価時は `render.render_user()` が
出力する user テキスト（確定した出目・合計・難易度・結果）を基準に忠実性を判断する。

## 3. カテゴリ別の評価項目

### 3.1 trpg_gm（GM応答）

| 項目 | 重点 |
|---|---|
| 1 JSON構文 | `narrative` + `choices`（3〜4個）必須、`assistant.content` がJSON1つだけ |
| 2 スキーマ | `GmResponseRules`: narrative ≤ 8000、sceneTitle ≤ 60、eventSummary ≤ 300、choices.id一意、check は `attribute/difficulty/rollMode/skillId` のみ |
| 3 ID参照 | `stateChanges.targetId` / `memories.relatedIds` / `npcMemories.npcId` / `check.skillId` が context 内に実在 |
| 4 数値・判定 | `total = ダイス(通常1個/有利不利2個) + attributeValue + skillLevel`、`difficulty ∈ {4,6,8,10,12,14}`、outcome 区分は仕様どおり。HP_DELTA ≠ 0 かつ ±100、XP ±1000、関係値 ±100 |
| 5 重複 | 同一 group の3ターンが言い換えだけになっていないか |
| 6 保護 | 出目・合計・結果を書き換えていない。自由入力に `check` が付いていない |
| 7 忠実性 | 描写が `action.text` と確定判定結果に沿う。成功/失敗の描写が判定と一致。選択肢が現在地・状況から実行可能 |
| 8 正確性 | context に無い事実・NPC・アイテムを出さない。新規アイテムは `ITEM_ADD.item` にだけ。`【GM専用】` をプレイヤーへ開示しない |
| 9 日本語 | `narrative` が情景＋口調で自然。150〜350文字は目安（上限ではない）。sceneTitle/eventSummary が本文と矛盾しない |
| 10 TRPG整合 | 敵HPを動かさない（HP_DELTAはPCのみ）、COMBAT_START/ENDの状態条件、クエストはACTIVEのみ進行、場所は戦闘中・現在地不可、記憶の category/isConfirmed/isSecret が妥当 |

### 3.2 world_json（世界観・設定）

| 項目 | 重点 |
|---|---|
| 1 JSON構文 | JSON1つだけ、コードフェンスなし、配列フィールドが文字列のままになっていない |
| 2 スキーマ | `WorldDraft` 16キー必須、`scenario` 5キー、`opening` 3キー、`location` 4キー、NPC 8キー（relationship は無い） |
| 3 ID参照 | `opening.location.connections` が本文・世界設定と無関係でない（名称解決は警告扱いだが、評価では辻褄を見る） |
| 4 数値 | `combat.hp` の受理上限は999（Kotlin）だが学習推奨は1〜30（**5.1.2**）、攻防0〜20、技能0〜3、`objectives/rewards` は文字列配列 |
| 5 重複 | 既存世界と名前・組織・謎が使い回しでない（`BATCH_THEMES.md` と突き合わせ） |
| 6 保護 | `scenarioPremise` というキーを作っていない。全角引用符や末尾カンマが無い |
| 7 忠実性 | request のキーワード・雰囲気・難易度・「NPC2〜4人／クエスト1〜3件」が反映されている |
| 8 正確性 | 実在作品の固有名詞を写さない。`secrets` がGM専用の真相で、プレイヤー既知の観測情報が入っていない |
| 9 日本語 | setting/history/geography が抽象的すぎず具体的。genre/era/techMagic が世界のトーンと一致 |
| 10 TRPG整合 | objective/problem/openingHook がつながる。戦闘NPCが1人だけ等、導入が遊べる構成 |

### 3.3 extraction（自然文→JSON抽出）

| 項目 | 重点 |
|---|---|
| 1 JSON構文 | `{"messages":[...], "metadata":{...}}`。assistant がコンパクトJSON |
| 2 スキーマ | 7タスクのうち指示された1つだけ。`memories` は `memories` と `npcMemories` の両方が必要 |
| 3 ID参照 | `targetId` / `relatedIds` / `npcId` が `context` に実在。存在しないIDは創作しない |
| 4 数値 | `quantity` 1〜99、`power/defense` 0〜20、`importance` 1〜5、`combat.hp` の受理上限999／学習推奨1〜30（**5.1.2**）、数詞（三つ/二個/十二）の変換 |
| 5 重複 | 同じ入力文の言い換えだけが量産されていない |
| 6 保護 | 否定文・条件文・未確定表現が変化していない（`check_protected_text.py compare`） |
| 7 忠実性 | 書かれていない項目は空配列／既定値。`state_changes` なら該当変更だけ、他タスクのキーを持ち込まない |
| 8 正確性 | 文章に無い人物・場所・報酬・効果・数値を足さない。`isConfirmed`（確定度）と `isSecret`（公開先）は独立に判定（**5.1.5**） |
| 9 日本語 | `content` が後から読んでも分かる一文。入力文の口調・文体を壊さない |
| 10 TRPG整合 | `ITEM_ADD` に id を付けない、敵HPを更新しない、名前が無い人物を作らない、クエスト objective が1件以上 |

## 4. 赤線（即 人間確認。点数で相殺しない）

次に該当するサンプルは合計点に関係なく「人間確認対象」とする。

1. 出目・合計・判定結果をモデルが創作している（user の確定結果と矛盾）。
2. 敵HPを変更している／`HP_DELTA` をNPCへ適用している。
3. context に存在しないID・NPC・場所・所持品を参照している。
4. 文章に無い事実・数値・人物を出力に追加している（特に抽出カテゴリ）。
5. `【GM専用】` の秘密をプレイヤー向け `narrative` に書いている。
6. 否定・条件・数値が入力と逆転している。
7. スキーマ error が1件でもある（この場合、そのサンプルは学習に使わない）。

## 5. 評価手順

1. 対象サンプルを選ぶ（274件をそのまま使ってよいが、正解ではなく検証サンプルとして扱う）。
2. 機械項目を計算し、項目ごとの点とエラー詳細を記録する。
3. 人手項目をカテゴリ別の観点で採点する。判断に迷ったら部分点ではなく「保留」として記録する。
4. 合計点と赤線を突き合わせ、**70点以下または赤線あり**を人間確認キューに入れる。
5. 判断が変わった理由（基準の解釈変更を含む）を記録し、次回の較正に反映する。

採点結果はサンプル単位で残すが、この定義書は点数のみを目的としない。
「なぜその点か」を説明できることが、品質管理の目的である。

## 5.1 判断が難しい5項目の定義

以下は評価者間で差が出やすいため、受理仕様と推奨仕様を分離して定義する。
いずれも既存のコード・プロンプト・スキーマを変更せず、この定義書側の解釈として記録する。

### 5.1.1 `Item.type` の正式な許容値

| 種別 | 値 | 根拠 |
|---|---|---|
| **受理仕様（Kotlin）** | `String`。空文字なら `misc` に正規化。それ以外の非空文字列は受理される。列挙ではない | `Skill.kt:31`, `DraftModels.kt:84`, `DraftParsers.kt:275` |
| **推奨仕様（学習データ）** | `weapon` / `armor` / `tool` / `consumable` / `misc` | `prompts.py:157,208` のスキーマ例 |
| 検証器 | `schema_lib.validate_items()` は `type` の値を検査しない | `schema_lib.py:696-714` |

**矛盾の扱い**: 受理は自由文字列、生成指示は5値のみ。
評価では「5値から外れる値は指示への忠実性（項目7）を減点するが、スキーマ error にはしない」。
`magic` / `material` は推奨値ではないため減点対象だが、Kotlin は受理する。

### 5.1.2 `combat.hp` の正式な上限

| 種別 | 範囲 | 根拠 |
|---|---|---|
| **受理仕様（Kotlin）** | 1〜**999** | `Npc.kt:24` の `CombatStats.MAX_HP = 999`、`DraftParsers.kt:164`、`BackupValidator.kt` |
| **推奨仕様（学習データ）** | 1〜**30** | `prompts.py:75`, `AdventureCreator.kt:298` |
| 検証器 | 1〜999 で error、31以上は warning | `schema_lib.py:597-598` |

**矛盾の扱い**: 「正式な受理上限は999、学習生成上の上限は30」と分離して記録する。
31〜999 はスキーマ error ではないが warning として人間確認対象とし、
学習データは1〜30に統一する（既存の不整合は解消済みではなく記録済みとする）。

### 5.1.3 簡体字検出の判定範囲

簡体字は Kotlin の契約ではなく、日本語品質の基準である。したがって「受理仕様」は存在せず、
2つの検査ツールの**検出範囲の違い**を明示する。

| ツール | 集計単位 | 文字集合・判定 | 評価での役割 |
|---|---|---|---|
| `check_simplified_chinese.py` | **出現回数** | 130文字を走査。`误` / `录` / `采` を含む。`采配` / `采女` はホワイトリストで除外。`装` / `双` / `践` は誤検出防止のため対象外 | **主**。項目6の減点はこの出現回数を使う |
| `check_protected_text.py scan` | **行数** | 独自の文字集合。その行に簡体字があれば1件として数える | **補助**。レビューする行を絞る目的でのみ使い、減点集計には使わない |

同じ実データで「8件（出現回数）」と「3件（行数）」になるのは集計単位の違いであり矛盾ではない。
「何箇所直すか」は出現回数、「どの行を見るか」は行数を使う。
文脈ホワイトリストの詳細は `training/specs/SIMPLIFIED_CHINESE_CHECK.md` を参照する。

### 5.1.4 GMの自然な補完と情報捏造の境界

| 種別 | 根拠 |
|---|---|
| 補完を認める根拠 | `prompts.py:21` 「不明点は既存設定から自然に補完する」 |
| 創作を禁ずる根拠 | `prompts.py:17` 「出目・合計・判定結果を創作しない」、同 `:171` 「書かれていない事実を創作しない」 |

**定義**:
- trpg_gm で許可される補完は、**contextの事実から一意に導ける詳細**（例: 雪上の二本の橇跡→荷を片側に寄せた隊商）と、
  **既知設定と矛盾しない感覚描写**（音・匂い・温度・視界）に限定する。
- 許可されないのは、contextに無い固有名詞・数値・ID・関係値・秘密・アイテムの追加
  （新規アイテムは `ITEM_ADD.item` にだけ書く）、および既知事実の否定である。
- 「一意に導ける」とは、多个の解釈が残らず、既存設定と矛盾しない場合に限る。
  解釈が複数ある場合は補完せず、状況を言い直すか未解決として残す。
- extraction では補完を一切認めず、該当なしは空配列とする。
- world_json は request からの設計・創作が主目的であり、上記の補完ルールの対象外である。

### 5.1.5 `isConfirmed` と `isSecret` の独立した判定

| 項目 | 意味 | true の条件 | 根拠 |
|---|---|---|---|
| `isConfirmed` | 事実の確定度 | 入力・contextで明示され、観測・発言・判定結果として確定しているもの。「らしい／かもしれない／気がする」は false | `Memory.kt:32` のコメント "true: confirmed fact, false: inference/proposal"、抽出プロンプトの「推測は false」 |
| `isSecret` | 公開先の制御 | プレイヤーに未公開の真相・黒幕・隠された事実。観測可能な情報は false かつ `secrets` に入れない | `Memory.kt:30` のコメント "GM-only information. Never rendered on player-facing screens."、抽出プロンプトの「GM専用の秘密は true」 |

両者は**独立した判定項目**である。
`isSecret: true, isConfirmed: true` は「GMだけが知る確定した真相」、
`isSecret: true, isConfirmed: false` は「GM専用の未確認な噂」として成立し得る。
片方をもう片方の代用にしてはならない。既定値はどちらも
`isSecret = false` / `isConfirmed = true`（`Memory.kt`, `GmResponse.kt`）だが、
意味の判定は `schema_lib` が行わないため人手項目（項目8・10）で確認する。

## 6. 判断が難しい項目（評価者間で差が出やすい）

| 項目 | 難しさ | 推奨する扱い |
